Enter squishling

Make your class squish. Just define your goal and output format, squishling does the rest.

Squishling.configure do |config|
  config.default_model = "claude-haiku-4-5-20251001"
  # falls back to RubyLLM's default when nil
end

class Parser
  include Squishling

  purpose "Map the inbound record onto the schema..."
  output_schema do
    string :patient_name
    string :patient_gender, enum: %w[male female trans unknown]
    array  :diagnosis_codes, of: :string
    array  :symptoms, of: :string
  end

  # no call method — every invocation is squished.
end

Run against all 100 fixtures:

pass: 73/100 cost: $0.48 / 100 calls

Beat

Squishling is Michael's own gem — built on this talk's own premise, the README cites the Substack article by name. A squished method either runs its Ruby implementation or, if there is none, routes straight to the LLM — "the method has no implementation" is a first-class routing rule, not a fallback hack. This class has no implementation at all. First real run, against all 100 fixtures: 73 pass (the original run, against just the first 35, was 23 pass — same purpose, same ~65% rate). On those original 35, every single diagnosis code — exact SNOMED codes, pulled out of four different shapes — came back correct; the failures clustered in three places: HL7 names came back untouched, a couple of gender codes, and a few hallucinated symptoms on records that should have reported none. The 65 added fixtures widen the failure surface to more exotic formats too. Name the failure modes out loud; the next two slides are about chasing them down for real, live, during prep for this talk.

Let's improve our pass rate!

class Parser
  include Squishling

  purpose <<~PURPOSE
    Map the record onto the schema below.

    Name: output "First Last" order, even if the source writes
    it as HL7's LAST^FIRST, often in all caps.

    Gender: translate to "male", "female", "trans", or "unknown".
    "unknown" for any code you don't recognize — including HL7's
    bare O / U / A / N letter codes. Never guess.

    Symptoms: only from an explicit symptom field. A diagnosis is
    not a symptom — never infer one from a diagnosis name.
  PURPOSE

  ...
end

Run against all 100 fixtures:

pass: 95/100 cost: $0.51 / 100 calls

Beat

Same class, same schema, same no-call-method trick — the only thing that changed is the purpose. Spelled out HL7's LAST^FIRST name convention, said explicitly that a diagnosis is not a symptom, and gave the gender translation concrete examples, including HL7's bare O/U/A/N letter codes. That alone took it from 23/35 to 31/35 on the original fixtures — 73/100 to 95/100 now that there are 100. The same two failure modes are still in there: letter codes and unlabeled SNOMED gender-identity codes the model structurally cannot resolve without a translation table, which v2's hand-written table still catches and v3 can't. The 65 added fixtures contribute exactly one more miss — a dictation transcript with diagnosis codes spoken as digits.

What if we ask twice?

class Parser
  include Squishling

  ...

  squishling escalation: ["claude-haiku-4-5", "claude-sonnet-5-5"],
    harness: { type: :judged_squishsum, judge: "claude-opus-5-5" }
end

Two samples per fixture, judge on disagreement:

pass: 95/100 cost: $1.02 / 100 calls

Beat

judged_squishsum samples the escalation's first step twice, concurrently, and only consults the judge when the two samples disagree. The second step declared here — Sonnet — is currently unused: on squishling's pinned commit, squishsum doesn't yet sample across different steps, so both samples are Haiku regardless of what else is in the escalation. Result: 95/100, $1.02 — the exact same five failures as a single attempt, at double the cost, and zero judge calls across all 100 fixtures. Same conclusion as every other same-model retry in this talk: at temperature 0.1, Haiku doesn't just usually agree with itself, it agreed on every fixture, including the five it got wrong, every time. These are systematic misreadings, not sampling noise — a harness built to catch disagreement never gets a chance to fire unless the samples actually come from different models.

Code the standard shapes. Squish the rest.

class Parser
  include Squishling

  ...
  squishling escalation: ["claude-haiku-4-5", "claude-sonnet-5-5"],
    harness: { type: :judged_squishsum, judge: "claude-opus-5-5" }

  def call(data)
    return fhir_parser.call(data) if fhir_message?(data)

    squish!
  end
end

Run against the same 100 fixtures:

pass: 95/100 cost: $0.12 / 100 calls

Beat

This is the whole optimization: one branch for the 63% that already match the canonical FHIR shape, routed straight to a fast, free, hand-written parser; the remaining 37% fall through to squishling — now with judged_squishsum instead of a single attempt. Real cost on these 100 fixtures: $0.12, versus $0.51 for squishing all 100 the old way — still a 76% discount. Pass rate stays flat at 95/100, same five misses as the single-attempt router: on the pinned commit, squishsum still samples the same step twice rather than two different ones, so Sonnet in the escalation above goes unused and the judge never gets consulted. Same honest edge as everywhere else in this talk — asking the same model twice doesn't catch what it confidently got wrong.

Even a bug in your own code can squish.

class SomeHelperMethod
  def call(payload)

  end

# oops calling method sent a string, not a hash

# => NoMethodError: undefined method 'dig' for an instance of String

class SomeHelperMethod
  include Squishling

  ...

  def call(payload)
    payload.dig("user", "email")
  rescue
    squish!
  end
end

SomeHelperMethod.call(payload)
# => "alice@example.com"

If the answer is in the stack trace somewhere, squish can find & return it!

Beat

This is not a vendor format problem — it is a plain old bug, the kind every engineer in the room has shipped. One caller sends "user" as a nested object, another flattens it to a string, and the dig call written for the first shape blows up on the second. Same squish! trick as the parse-failure rescue, just caught by a bare rescue instead of one scoped to a specific error class. The point is not "squishling fixes bugs" — it is that any rescued exception, including ones from your own code, can be the trigger.

Squishling Roadmap

  • Framework-specific defaults.
  • Support non-RubyLLM implementations.
  • Output format annotations.

Earlier in this talk, a harness that didn't exist yet — judged_ensemble — got filed and shipped the same day. Framework-specific defaults: sensible params, logging, and squawk wiring out of the box for Rails, Sinatra, and friends, instead of every app hand-rolling the same Squishling.configure block this demo did five times. Output format annotations: metadata on individual schema fields — units, examples, provenance hints — so the purpose doesn't have to spell out in prose what the schema could just say directly. Elastic Software: Calculating tech debt using LLM tokens

A talk by Michael Carroll, founder of Coolhand Labs, given at XO Ruby NYC in October 2026.

We have never been able to price tech debt

If you have been working in engineering long enough, you have spent some double-digit percentage of your working life thinking about tech debt, and complaining about it. We should pay some down before we build this. Our estimates were wrong because of historical tech debt. Reason for leaving: too much tech debt.

Product managers roll their eyes when engineers say the words, and honestly they have earned the right. We are bad at describing what tech debt is, and we are far worse at quantifying what it costs to fix it or to carry it. We have been asking for budget in a currency nobody outside engineering can read. To borrow from Justice Potter Stewart: I don't know how to quantify it, but I know it when I see it.

The pattern: a parser for every client

Here is the shape of the problem, from my own history building health care software at RubiconMD. You build a standard patient data integration — FHIR, or something like it. You tell a clinical client you have data integration and you sign a contract. Then you discover that they implement the standard a little differently, or that some of their data does not come through the integration at all. So you build a custom parser for their unique standard, and you monitor it, and you update it as they break it. And you allow yourself to believe that this parser will now cover you for all future clients — a hope that is dashed by every single new contract.

A hundred clients later you have thousands of lines of code that dispatch on a client name through a case statement nobody can read. And the real bill is not the lines of code. It is that every new client is blocked on a discovery and sample-data cycle; that parsers break silently when a client ships a change; that some engineer's quarter has quietly become parser babysitting; and that your best sales month creates your worst backlog.

That is tech debt — and every word of that description is a feeling. None of it is a number a CFO can act on.

Tokenomics: putting a number on it

We have always had two ways to do this work: pay an engineer to write and own a parser, or pay a machine to handle the record. What is new is that both sides can now be denominated in the same unit.

On the software side, you can itemize what one parser actually costs: the time to write it, code review and QA, the ongoing drag of bug reports and maintenance cycles, and the new data type that lands six months later. Those are real engineering hours, and in an AI-assisted shop those hours increasingly carry a token-equivalent cost too. On the AI side, you know your average cost per request for each integration. Break it down by client, multiply by volume, project it forward on your growth assumptions, and you have a clean, compounding monthly and annual number.

So the comparison gets refreshingly boring. AI path: $X per month, scaling with volume. Software path: $Y to build, $Z per month to carry. Tech debt just became arithmetic.

This does not capture every variable — not the cognitive load of one more system to hold in your head, not the context-switching tax, not the morale cost of asking a good engineer to babysit another brittle parser. But you do not need all of them. You need a signal strong enough to make a call you can defend to your product and engineering teams and to your CFO.

The inversion

The obvious lesson to draw from all this is the wrong one. It is not "use AI coding agents to write the parsers faster" — that is using AI to produce more of the thing that is hurting you. The actual move is to invert the priorities: make flexibility the default, and efficiency the optimization.

In practice that means the parser call delegates to an AI parser, and the AI parser is roughly a dozen lines of Ruby using a gem like RubyLLM: a cheap model, a low temperature, an instruction to map the inbound record to your internal schema and return only valid JSON with nulls for anything missing, and a JSON parse on the way out. It will choke a few times, and you will tune the prompt against real failures, but you have a functioning parser in minutes.

What disappears is most of the seven-step pattern. There is no discovery cycle, no "please send us sample data to test the integration with." The remaining blocker on a new client is whether you have signed the BAA with your inference provider.

Contracting toward efficiency

Then the bill arrives, because running inference on one hundred percent of inbound volume gets expensive. This is the honest middle of the pattern, not a failure of it. Typically a handful of clients account for the vast majority of your volume. Find them, use the production data you have been gathering to write a genuinely good spec, build hardened parsers for those, and let everything else keep flowing through the model.

The result looks like the case statement you started with — except it has two branches instead of a hundred, and the data told you to write both of them. That is the elasticity: you start stretched all the way toward flexibility, accepting a higher cost per request in exchange for speed, and you contract toward efficiency as the math justifies it. You do it independently for each integration, each data type, each client. Never all at once, and never up front.

The decision rule fits in one sentence: when projected annual inference cost for an integration exceeds what it would cost to build and carry a parser for it, you have a candidate. Startups have always practiced a crude version of this — "doing things that don't scale" is the same pattern with humans in the flexible layer — but the math was always fuzzy. What you need to run it deliberately is cost per request broken out by client, visible without anyone assembling a spreadsheet by hand. That is the frustration Coolhand Labs came out of; the pattern and the product were shaped by the same annoyance.

The real win is speed

Optimizing cost is useful, but for a startup it is the smaller half of the story. Close five new hospital systems in a month and, in the old world, that is a scramble disguised as a celebration: who do we build parsers for first, how do we sequence it, how long until they go live and we can realize the revenue? In the elastic model all five go live immediately, the AI layer carries their data from day one, and you start collecting the only thing that can actually tell you who deserves engineering time. If one turns out to be a monster account, the tokenomics surface it quickly. If one churns in month two, you never wasted a line of parser code on it.

It runs in the other direction too. If you are an enterprise drowning under a thousand legacy parsers, find the ones sitting at the tail of your usage curve, re-route them to an inference call, and delete the code.

Proving it for real

Two malformed records through a dozen lines of Ruby is a good trailer. The real test is 35 real patients — pulled from actual Synthea-generated FHIR bundles, not invented — rendered into four genuinely different wire formats: a canonical FHIR bundle, a re-keyed FHIR variant with different field names, an HL7 v2.3 message, and a legacy pipe-delimited flat file. Each one carries real-shaped noise: extra FHIR extensions, extra HL7 segments nobody asked for, a dozen irrelevant flat-file columns. Twenty of the 35 share one shape; the other 15 each use a shape the parser has never seen.

Pointed at that data, v1 — the "day one, it is beautiful" parser, verbatim — gets 20 of 35, and fails cleanly, not a crash, on the 15 it was never built for. v2 is the monster case statement's honest descendant: a base class, one subclass per format, a dispatcher, and a gender-translation table grounded in real FHIR, HL7, and SNOMED code systems. It gets all 35. It is also four classes and a shared translation module — real, maintained code, for four formats.

Then the same problem, handed to a squishling — a gem built on this talk's own premise, whose class declares a purpose and an output schema and nothing else. No shapes, no classes, no translation table: a method with no implementation is squished straight to the LLM by default. First real run against all 35: 23 pass. Every diagnosis code — exact SNOMED codes, pulled out of four different shapes — came back right; the failures clustered in HL7 names coming back untouched, a few gender codes, and a handful of hallucinated symptoms on records that should have reported none.

Reporting that hallucination, live, during prep for this talk, got a same-day fix: temperature and other generation params, added to the gem. Rerunning at a low temperature produced the exact same 23 — the same 12 files failed, and one record that had passed by luck now failed every time. That flip was the tell: this was never sampling noise. The model was systematically treating "diagnoses nearby, no symptom entry" as license to invent one; a lower temperature just made the wrong call more reliable, not less.

The actual fix was the purpose — spelling out, in plain language, the things v2's code already knew by construction: HL7 writes names LAST^FIRST, a diagnosis is not a symptom, and what an unfamiliar gender code should default to. That got it to 31 of 35. A prompt is code too, and it benefits from the same iteration a case statement would. The last four are the honest edge of it: two bare gender-identity codes with no label attached, where the model correctly refuses to guess rather than fabricate an identity — v2 only gets these right because it was handed the mapping by hand — and two HL7 letter codes it still misreads despite being told exactly what they mean. Code is exact because you give it the answer; the model is elastic because it has to infer one.

The hard problems are still wide open

A lot here is still emerging, and these are the questions I get asked by teams implementing some version of this. What are the real failure modes, and what does good monitoring look like across a hybrid system with AI and hardened software paths running side by side? How do you handle drift — the AI layer quietly making different mapping decisions this month than it made last month, with no diff to review? What is the right ops sampling rate to catch a prompt regression before it compounds into a thousand mis-mapped records? And how do these patterns survive contact with regulated environments, where failures have to be justified to an auditor?

These are not rhetorical. The teams I see doing this well are working them out in real time. What separates them is not that they have the answers — it is that they treat elastic software as a genuine architectural commitment, with the monitoring and discipline that implies, rather than a clever hack they bolted on to ship faster and hoped nobody would ask about later.

If you are building on this pattern, or fighting with it, I would like to hear where it is breaking for you. That is the actual reason I am up here.
