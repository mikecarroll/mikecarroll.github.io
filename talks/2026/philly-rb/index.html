Enter squishling

Make your class squish. Just define your goal and output format, squishling does the rest.

Squishling.configure do |config|
  config.default_model = "claude-haiku-4-5-20251001"
  # falls back to the adapter's default when nil
end

class Parser
  include Squishling

  purpose "Map the inbound record onto the schema..."
  output_schema do
    string :patient_name
    string :patient_gender, enum: %w[male female trans unknown]
    array  :diagnosis_codes, of: :string
    array  :symptoms, of: :string
  end

  # no call method — every invocation is squished.
end

Run against all 100 fixtures:

pass: 73/100 cost: $0.48 / 100 calls

Beat

Squishling is Michael's own gem — built on this talk's own premise, the README cites the Substack article by name. A squished method either runs its Ruby implementation or, if there is none, routes straight to the LLM — "the method has no implementation" is a first-class routing rule, not a fallback hack. This class has no implementation at all. First real run, against all 100 fixtures: 73 pass (the original run, against just the first 35, was 23 pass — same purpose, same ~65% rate). On those original 35, every single diagnosis code — exact SNOMED codes, pulled out of four different shapes — came back correct; the failures clustered in three places: HL7 names came back untouched, a couple of gender codes, and a few hallucinated symptoms on records that should have reported none. The 65 added fixtures widen the failure surface to more exotic formats too. Name the failure modes out loud; the next two slides are about chasing them down for real, live, during prep for this talk.

Let's improve our pass rate!

class Parser
  include Squishling

  purpose <<~PURPOSE
    Map the record onto the schema below.

    Name: output "First Last" order, even if the source writes
    it as HL7's LAST^FIRST, often in all caps.

    Gender: translate to "male", "female", "trans", or "unknown".
    "unknown" for any code you don't recognize — including HL7's
    bare O / U / A / N letter codes. Never guess.

    Symptoms: only from an explicit symptom field. A diagnosis is
    not a symptom — never infer one from a diagnosis name.
  PURPOSE

  ...
end

pass: 95/100 cost: $0.51 / 100 calls

Beat

judged_squishsum samples the escalation's first step twice, concurrently, and only consults the judge when the two samples disagree. The second step declared here — Sonnet — is currently unused: on squishling's pinned commit, squishsum doesn't yet sample across different steps, so both samples are Haiku regardless of what else is in the escalation. Result: 95/100, $1.02 — the exact same five failures as a single attempt, at double the cost, and zero judge calls across all 100 fixtures. Same conclusion as every other same-model retry in this talk: at temperature 0.1, Haiku doesn't just usually agree with itself, it agreed on every fixture, including the five it got wrong, every time. These are systematic misreadings, not sampling noise — a harness built to catch disagreement never gets a chance to fire unless the samples actually come from different models.

Even a bug in your own code can squish.

class SomeHelperMethod
  def call(payload)
    payload.dig("user", "email")
  end
end

payload = { "user" => "alice@example.com" }
# oops calling method sent a string, not a hash

SomeHelperMethod.call(payload)
# => NoMethodError: undefined method 'dig' for an instance of String

class SomeHelperMethod
  include Squishling

  ...
  append_to_purpose "The code it runs:", self

  def call(payload)
    payload.dig("user", "email")
  rescue => e
    squish!(context: { error: e })
  end
end

SomeHelperMethod.call(payload)
# => "alice@example.com"

If the answer is in the stack trace somewhere, squish can find & return it!

Beat

This is not a vendor format problem — it is a plain old bug, the kind every engineer in the room has shipped. One caller sends "user" as a nested object, another flattens it to a string, and the dig call written for the first shape blows up on the second. Same squish! trick as the parse-failure rescue, just caught by a bare rescue instead of one scoped to a specific error class. Two lines do the work: append_to_purpose "...", self puts this class's own source into the prompt, and squish!(context: { error: e }) sends the raised error along with the arguments, so the model sees the code, the input and the exact failure. The point is not "squishling fixes bugs" — it is that any rescued exception, including ones from your own code, can be the trigger.

Squishling: LLM Power-Ups for Ruby Classes

A talk by Michael Carroll, founder of Coolhand Labs, given at Philly.rb in November 2026.

Flexibility is a known engineering trick

Skyscrapers sway on purpose. Sidewalks get a strip of soft putty at every expansion joint. A car's frame is designed to crumple. In every case, a little deliberate softness is what keeps the rigid parts from cracking under load. Softness and flexibility add resilience in engineering — that is not controversial once you say it about concrete and steel.

Now say it about tech debt. Ask a room whether tech debt is good or bad and you get a chorus of "bad." Ask about a credit card and the room splits. Ask about a mortgage and it usually flips to "good." The answer was never really about the debt — it was about whether it was leverage, taken on deliberately and paid down on purpose, or just debt, taken on carelessly. Tech debt can be an asset or a liability depending on what you do with it. But that just restates the real problem: it's hard to quantify the advantage tech debt gives you if you can't first quantify the cost of carrying it.

Health tech, 2010s: the parser that could not stay clean

Here is the shape of the problem, from my own history building health care software at RubiconMD. You sign a clinical client. You need their patient data in your system. There is a standard for this — FHIR. Easy peasy. Day one, the parser is a single clean method: hand it the data, call fhir_parser, done.

A hundred clients later, that one line has become a case statement with a branch per client, running on so long the slide itself becomes illegible — which is the point. You stop trying to read it long before anyone finishes writing it. And it does not matter whether a person or an AI coding agent wrote that case statement: it is terrible software architecture either way. It is hard to DRY, any data format change can break it, every breakage is a scramble, it adds cost to every new contract, and the more clients you sell the worse it gets. That is the worst kind of debt — uncontrollable, unavoidable, and unmanageable.

Swap the parser for an LLM call

Let's try this again. Same method, same signature — comment out fhir_parser.call(data) and replace it with a RubyLLM call: instructions describing the record, a schema describing what should come back. The call site never changes; only what's inside it does.

The gut reaction is to recoil — handing parsing to a model feels wrong on first sight. But look at what you just bought: zero brittle code, instant integration, and the flexibility to handle external factors you can't change. Then the second objection lands right behind the first: won't this cost a lot of money in LLM tokens? The answer is the actual thesis of this talk — refactor the high-volume paths back into deterministic code, keep AI for everything else, and for the first time your tech debt has a quantity you can measure.

Enter squishling

Wouldn't it be nice if there were an elegant Ruby DSL for managing and tuning exactly that code/AI hybrid? That's squishling — my own gem, built directly on this talk's premise. Don't just use AI to write code; use AI to not need code. A squishling class declares a purpose and an output_schema and nothing else — no call method at all. A method with no implementation is squished straight to the LLM by default.

First real run against all 100 fixtures — real Synthea-generated FHIR patients, rendered into dozens of genuinely different wire shapes, from canonical FHIR and HL7 v2.3 down to a PDF, an OCR'd fax transcript, a SOAP note, and a plain SMS chat log: 73 pass, for forty-eight cents across all 100 calls. Every diagnosis code — exact SNOMED codes, pulled out of wildly different shapes — came back right. The failures clustered in three places: HL7 names coming back untouched, a few mis-translated gender codes, and a handful of hallucinated symptoms on records that should have reported none.

The fix was not more code — squishling has none to fix. It was the purpose: spelling out, in plain language, what a hand-written parser would have known by construction. HL7 writes names LAST^FIRST, often in all caps. A diagnosis is not a symptom — never infer one from a diagnosis name. An unrecognized gender code, including HL7's bare O/U/A/N letters, maps to "unknown," never a guess. Same class, same schema, same no-call-method trick — only the purpose changed, and the pass rate jumped to 95 of 100, for 51 cents. A prompt is code too, and it benefits from the same iteration a case statement would.

What if we ask twice?

During prep for this talk I filed an issue for a harness squishling didn't have yet — sample two different models and have a third judge disagreements — and squishling's maintainer shipped it the same day. Wiring it up on the pinned commit, though, surfaced an honest gap: the harness samples the escalation's first step twice, concurrently, rather than sampling two different steps. So a second model declared in the escalation sits unused — both samples come from the same model regardless.

Run it anyway: 95 of 100, the exact same five failures as a single attempt, at double the cost — $1.02 — and zero judge calls across all 100 fixtures. At a low temperature, that one model doesn't just usually agree with itself; it agreed on every fixture, including the five it got wrong, every single time. These are systematic misreadings, not sampling noise — a harness built to catch disagreement never gets a chance to fire unless the samples actually come from different models.

The elastic slider, and the router

A quick analysis of the data shows 63% of requests fit the standard canonical FHIR shape. That's the elasticity, drawn as a slider between fully flexible (the model handles everything, at a higher cost per request) and fully efficient (a hardened parser, cost near zero) — and the position on that slider is a decision you keep revisiting per integration, not a bet you place once at design time.

So: code the standard shapes, squish the rest. One branch routes the 63% that already match canonical FHIR straight to a fast, free, hand-written parser; the other 37% fall through to squishling. Same 100 fixtures, same 95 pass rate, 12 cents — a 76% discount over squishing everything, with the same five honest misses, because the pinned harness still samples one model twice. The payoff: integrations work on day one, cost per request stays low, and total LLM cost lands well below what the equivalent maintenance would have cost — without a rewrite, a re-architecture, or a bet placed up front.

It runs backward too. If you're an enterprise drowning under a thousand legacy parsers, find the ones sitting at the tail of your usage curve, squish them instead, and delete the code.

It was never just about health data

"Yeah, cool, but we don't need to parse health data." Fair — but do you integrate with services? Every vendor integration has this exact same shape. When a vendor webhook payload breaks your hand-written parser, rescue the parse error and squish! it — same trick as the FHIR router, just triggered by an exception instead of a format check, straight out of squishling's own README.

"We don't integrate with services or APIs either." Then are you hiring? And more seriously: do you ever have production errors? Because the same trick catches those too — even a plain bug in your own code, a dig call written for one shape that blows up on another, can rescue into a squish! and come back with the right answer pulled straight out of the stack trace. Any rescued exception, including ones from your own code, can be the trigger.

What's next for squishling — and the ask

The last roadmap shipped: Bring Your Own Harness and non-RubyLLM adapters are both out. What's next is A/B testing of code and model pathways; native Rails error integration and rescue; a squishy benchmarks registry; and a "forever services" bootstrapper. The last item is only half a joke: this entire demo leaned on me personally generating mascot art on request, and that does not scale past one deck.

If any of that sounds useful: squish the star button on github.com/Coolhand-Labs/squishling, share it, and leave an issue. I'd genuinely like to know where this pattern is breaking for you — that's the actual reason I'm up here.

Three lessons from the rescue tests

First, small models are still bad at math: extract raw values with the model and compute dates and totals in Ruby. Second, give the models an escape hatch: when the input held no answer, every model invented a schema-valid value instead of failing, so add an unknown option, a nullable field, or a squish_fallback. Third, Apple FM is not a great model yet: it passed 20 of 100 fixtures on its own and 82 of 100 behind a router, for free.

What's new in squishling since XO Ruby NYC

Squishling 0.3.0 shipped the day of the first version of this talk, with the squishsum and judged_squishsum harnesses, the squawk hook, and instructions renamed to purpose. 0.4.0 added custom harnesses, round-robin model tiers, and a built-in Coolhand observer, and removed the :ensemble harnesses. 0.5.0 and 0.5.1 added pluggable adapters (RubyLLM, any OpenAI-compatible endpoint, plus separate Apple Foundation Models and Claude Code adapter gems), per-call token budgets, Squishling.verify, testing helpers, and security hardening of error messages. 0.6.0 turned prompt caching on by default: in a 20-fixture test on Claude Haiku 4.5 it cost 21 percent more on the first pass and 76 percent less when the same inputs repeated. The biggest change is local models: the same squishling class can run on Apple's on-device model for $0.
